## 1. PLP/SRP 통합

### 최종 결정
MVP에서는 상품 목록 페이지(PLP)와 검색 결과 페이지(SRP)를 동일한 UI 컴포넌트와 API로 처리

### 검토 배경
- 별도 구현 시 개발 공수 증가
- 두 페이지의 핵심 기능이 유사 (상품 목록 + 필터 + 정렬)

### 기존 검토안
| 옵션 | 설명 |
|------|------|
| A. 완전 분리 | /products (PLP), /search (SRP) 별도 구현 |
| B. 통합 | 동일 컴포넌트, 쿼리 파라미터로 구분 |

### 결정 이유
- MVP 개발 속도 우선
- UI/UX 일관성 확보
- Post-MVP에서 검색 고도화 시 분리 가능

### Post-MVP 계획
- 검색엔진 도입 시 SRP 분리 검토
- 검색 전용 UI/UX 개선

## 2. 검색 MVP 범위

### 최종 결정
PostgreSQL ILIKE 기반 단순 검색만 구현 (검색엔진 없음)

### 검토 배경
- 초기 상품 수 100개 미만 예상
- 검색엔진 도입 비용 및 복잡도

### 기존 검토안
| 옵션 | 비용 | 기능 |
|------|------|------|
| A. PostgreSQL ILIKE | 무료 | 기본 키워드 매칭 |
| B. Elasticsearch | 유료 | 자동완성, 오타교정, 유사어 |
| C. Algolia | 유료 | 관리형 검색 서비스 |

### 결정 이유
- 저비용 운영 원칙에 부합
- 초기 상품 수에서는 ILIKE로 충분
- 검색엔진은 검증 후 도입

### Post-MVP 계획
- 상품 500개 이상 시 검색엔진 도입 검토
- 검색 로그 분석으로 개선점 파악

## 3. URL 구조

### 최종 결정
단일 라우트 `/products/[...slug]` 사용, 카테고리와 검색은 쿼리 파라미터로 처리

### 검토 배경
- SEO와 사용자 경험 모두 고려 필요
- SvelteKit 라우팅 구조와의 호환성

### 기존 검토안
| 옵션 | URL 예시 |
|------|----------|
| A. 분리 라우트 | /category/outer, /search?q=니트 |
| B. 통합 라우트 | /products?category=outer&q=니트 |
| C. 슬러그 기반 | /products/outer, /products?q=니트 |

### 결정 이유
- 구현 단순화
- 필터 조합의 유연성
- SEO에 큰 영향 없음 (카테고리 페이지 별도 메타 태그)

### Post-MVP 계획
- /category/outer → /products?category=outer 리다이렉트 추가 가능
- SEO 분석 후 URL 구조 최적화

## 4. SKU 변경 정책

### 최종 결정
SKU 변경 가능하나, Midas ERP 동기화 시 매핑 오류 가능성 경고

### 검토 배경
- Midas ERP에서 SKU를 Primary Key로 사용
- 운영 중 SKU 변경 필요 케이스 존재

### 기존 검토안
| 옵션 | 장점 | 단점 |
|------|------|------|
| A. 변경 불가 | ERP 동기화 안전 | 운영 유연성 감소 |
| B. 변경 가능 + 경고 | 운영 유연성 확보 | 동기화 오류 가능 |
| C. 변경 시 이력 관리 | 추적 가능 | 구현 복잡도 증가 |

### 결정 이유
- 운영 유연성 확보
- 경고 메시지로 리스크 인지
- Midas 동기화 전 SKU 확정 권장

### Post-MVP 계획
- SKU 변경 이력 추적 기능
- Midas 동기화 시 SKU 매핑 검증

## 5. 재고 흐름

### 최종 결정
Midas ERP → 쇼핑몰 단방향 동기화. 엑셀 일괄 업로드 방식

### 검토 배경
- Midas가 재고의 원천(Source of Truth)
- 실시간 동기화 필요성 vs 복잡도

### 기존 검토안
| 옵션 | 방식 | 복잡도 |
|------|------|--------|
| A. 단방향 (수동) | 엑셀 업로드 | 낮음 |
| B. 단방향 (자동) | API 연동 | 중간 |
| C. 양방향 | 실시간 동기화 | 높음 |

### 결정 이유
- Midas API 연동 범위 미정
- 엑셀 방식으로 빠른 MVP 출시
- 추후 API 연동으로 업그레이드 가능

### Post-MVP 계획
- Midas API 연동 검토
- 실시간 재고 동기화
- 재고 불일치 알림

TipTap 에디터 사용, 기본 서식만 지원 (굵게/이탤릭/리스트/링크)

## 7. 할인가 입력

### 최종 결정
할인가 직접 입력 + 할인율로 계산 모두 지원. 5,000원 단위 반올림 적용

### 검토 배경
- 마케팅팀의 가격 설정 편의성
- 다양한 할인 전략 지원 필요

### 기존 검토안
| 옵션 | 입력 방식 |
|------|-----------|
| A. 직접 입력만 | 할인가 직접 입력 |
| B. 할인율만 | 할인율 입력 → 자동 계산 |
| C. 둘 다 지원 | 직접 입력 또는 할인율 선택 |

### 결정 이유
- 운영 편의성 최대화
- 5,000원 단위 반올림으로 가격 일관성
- 두 방식 모두 실무에서 필요

### 계산 로직
```javascript
// 할인율 → 할인가 계산 (5,000원 단위 반올림)
할인가 = Math.round(정가 × (1 - 할인율/100) / 5000) × 5000

// 예시: 정가 89,000원, 할인율 30%
// 89,000 × 0.7 = 62,300 → 60,000원
```

## 8. 상품 구조

### 최종 결정
옵션 방식 채택. ProductGroup 없이 단일 상품에 색상/사이즈 옵션으로 관리

### 검토 배경
- 패션 이커머스의 일반적인 상품 구조
- 색상별 별도 상품 vs 옵션으로 통합

### 기존 검토안
| 옵션 | 구조 | 예시 |
|------|------|------|
| A. 개별 상품 | 색상별 별도 상품 | 니트(블랙), 니트(화이트) |
| B. ProductGroup | 그룹 + 상품 + 옵션 | 복잡한 3단계 구조 |
| C. 옵션 방식 | 상품 + 옵션(SKU) | 니트 → 블랙/M, 블랙/L... |

### 결정 이유
- 구조 단순화
- 패션 이커머스 표준 방식
- 관리 용이성

### 데이터 모델
```
Product (상품)
└── ProductOption (SKU)
    - color: 색상
    - size: 사이즈
    - sku: 재고관리코드
    - stock_quantity: 재고
```
